# Brief: In-memory memo notes

## Goal

Add a small HTTP API so a client can **create and read a memo note** stored only
in process memory. This is a new resource (not a greeting, farewell, or
counter). Use it to exercise **layered architecture** in this repo, which today
keeps controller + service in one feature package.

Keep `GET /health`, greetings, farewells, and counters unchanged.

## In scope

1. **`POST /api/v1/notes`**
   - Request body (JSON):
     ```json
     { "text": "Ship the plugin test" }
     ```
   - `text` — required; trim whitespace; after trim: length 1–200 inclusive
   - Blank or missing `text` → `400` with the **same** JSON problem body as
     greetings (`error: "validation_failed"`, `details[].field` = `"text"`)
   - Too-long `text` → `400`, same envelope, field `"text"`
   - Success `201` with JSON:
     ```json
     {
       "id": "<uuid>",
       "text": "Ship the plugin test",
       "createdAt": "<ISO-8601 UTC timestamp>"
     }
     ```
   - `id` is a UUID generated by the service (not client-supplied)
   - Response `text` is the trimmed value

2. **`GET /api/v1/notes/{id}`**
   - `{id}` must be a UUID; malformed id → `400` `validation_failed` (field `"id"`)
   - Success `200` with the same JSON shape as create
   - Unknown id → `404` with the **same envelope as counters**:
     ```json
     {
       "error": "not_found",
       "details": [
         { "field": "id", "message": "note does not exist" }
       ]
     }
     ```

3. **Wrong HTTP method** on these paths may use framework defaults.

4. Existing **413 payload-too-large** filter (4096 bytes) already applies
   globally; do not add a second size check.

## Out of scope / non-goals

- Persistence / DB / files — notes are lost on process restart
- Auth / API keys
- List-all, update, delete, tags, author, pagination
- Client-supplied ids
- Changing `/health`, greetings, farewells, or counters
- Refactoring existing features into layers
- Rate limiting, OpenAPI/Swagger UI
- Deployment / CI beyond what already exists

## Constraints

- Stay on the **existing** Java 21 + Spring Boot 4.1.0 stack already in this repo
  (do **not** silently change major Boot version; if a change is required,
  update architecture + impl-plan in the same change — Decision Drift).
- **Layered architecture is required** for this feature (not the current
  single-package controller+service shape used by greeting/farewell/counter).
  Four layers, dependencies only **inward**:

  | Layer | Responsibility | Must not |
  | --- | --- | --- |
  | **Web** | HTTP: routes, JSON DTOs, status codes, mapping to/from application | Hold note store or UUID/text rules |
  | **Application** | Use cases: create note, get note | Depend on Servlet / Spring Web types |
  | **Domain** | Note identity + text invariants | Depend on Spring Web or a concrete store |
  | **Infrastructure** | In-memory repository implementing a port defined inward | Be called from Web, skipping Application |

  Package layout must make layers visible (e.g. `…notes.web` / `…notes.application`
  / `…notes.domain` / `…notes.infrastructure`). Architecture doc must name these
  layer boundaries; impl-plan must not collapse them into one package.
- Reuse the existing `400` `validation_failed` JSON shape; reuse the counter
  `404` `not_found` envelope (same `error` + `details` fields). Do not invent a
  third error document type.
- Unit / WebMvc tests required for:
  - create → `201` + trimmed text + UUID `id`
  - get after create → `200` same body
  - blank / too-long `text` → `400`
  - unknown id → `404`
  - malformed id → `400`
  - health, greetings, farewells, counters still work (regression)
  - a test or review check that Web does not depend on Infrastructure
    (no compile-time import from `notes.web` to `notes.infrastructure`)

## Unchanged contracts

- `GET /health` — `200`, `text/plain`, body `ok`
- `POST /api/v1/greetings` / `POST /api/v1/farewells` — existing JSON contracts
- Counter increment + get — existing JSON contracts
- `413` oversized body (`payload_too_large`, max 4096 bytes) for POST endpoints

## Acceptance criteria

- [ ] `POST /api/v1/notes` returns `201` + `{ id, text, createdAt }` with trimmed text and a UUID `id`
- [ ] `GET /api/v1/notes/{id}` returns `200` for an existing note and `404` for a missing one
- [ ] Invalid `text` / malformed `id` return `400` with `validation_failed`
- [ ] Code is split into web / application / domain / infrastructure packages with inward-only dependencies
- [ ] Existing health, greeting, farewell, and counter contracts still pass
- [ ] Tests cover happy paths, validation/`404`, layering, and regressions, and pass via project build
- [ ] Architecture + impl-plan docs exist under `docs/` and describe the four layers
- [ ] README mentions the new endpoints briefly (methods, paths, example)
